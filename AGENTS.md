# AGENTS.md — Cluster Resource Override Admission Operator

This file provides context for AI agents and tools working in this repository.
For human contribution guidelines, see [CONTRIBUTING.md](./CONTRIBUTING.md).

## Project Overview

The Cluster Resource Override (CRO) Admission Operator is an OpenShift operator that deploys and manages the CRO admission webhook server.
The admission webhook intercepts pod **create and update** requests and mutates resource requests/limits based on configured ratios, allowing cluster administrators to control the level of resource overcommitment across the cluster.

The operator watches for `ClusterResourceOverride` custom resources (cluster-scoped, singleton named `cluster`) and ensures the admission webhook server is deployed with the correct configuration.
When the CR is created or updated, the operator reconciles a Deployment running the webhook server, a Service, a MutatingWebhookConfiguration, an APIService, a ValidatingAdmissionPolicy (with Binding), and a ConfigMap with the override configuration.
Serving TLS certificates are not generated by this operator — the Service is annotated with `service.alpha.openshift.io/serving-cert-secret-name` so the OpenShift service-ca operator issues a signed certificate into a Secret.

The operator also supports namespace-scoped `ResourceOverride` resources (API group `autoscaling.openshift.io/v1`) for finer-grained per-namespace overrides with optional pod selectors.
Pod-to-selector matching is performed by the admission webhook (operand), not by this operator; the operator only validates `podSelector` syntax.
The admission webhook server itself lives in a separate repository: [openshift/cluster-resource-override-admission](https://github.com/openshift/cluster-resource-override-admission).

## Architecture: What Is Not Obvious

### Reconciliation Handler Chain

The `ClusterResourceOverride` controller uses a handler chain pattern, not a single monolithic reconcile function.
The chain is defined in `pkg/clusterresourceoverride/internal/reconciler/reconciler.go` and executes handlers in sequence:

1. **AvailabilityHandler** — checks operand Deployment availability and sets the `Available` status condition
2. **ValidationHandler** — validates the CR spec parameters
3. **ConfigurationHandler** — creates/updates the ConfigMap with override configuration
4. **ServiceHandler** — ensures the operand Service exists (annotated for service-ca TLS)
5. **DeploymentHandler** — ensures the operand Deployment exists with correct image and configuration
6. **DeploymentReadyHandler** — waits for the Deployment to become available
7. **APIServiceHandler** — registers the APIService for the admission endpoint
8. **WebhookConfigurationHandler** — creates/updates the MutatingWebhookConfiguration
9. **ValidatingAdmissionPolicyHandler** — creates/updates a ValidatingAdmissionPolicy + Binding that reject `ResourceOverride` creation in system namespaces (`openshift`, `openshift-*`, `kube`, `kube-*`, `kubernetes`, `kubernetes-*`)
10. **AvailabilityHandler** — same handler instance as step 1, run again at the end of the chain

Each handler receives the current CR copy and reconcile context, and can modify the CR status.
If any handler returns an error or requests requeue, the chain stops.
Later handlers may assume earlier handlers succeeded.

### Singleton Operand

The `ClusterResourceOverride` CR is a cluster-scoped singleton.
The reconciler only processes the CR named `cluster` (defined as `DefaultCR` in `pkg/operator/run.go`).
Requests for any other name are skipped (logged at `V(2)` as `"skipping reconcile"`).

### Two Controllers, One Binary

The operator runs two controllers in a single binary:
- `clusterresourceoverride` — manages the cluster-wide webhook based on `ClusterResourceOverride` CRs
- `resourceoverride` — manages namespace-scoped `ResourceOverride` CRs and watches namespace events

Both controllers are started by `pkg/operator/run.go`.

### Ownership and Secondary Resource Watching

The operator sets standard Kubernetes **`ownerReferences`** on resources it creates (see `pkg/runtime/ownership.go` → `SetController`).
A cluster-scoped `ClusterResourceOverride` CR can own both cluster-scoped dependents (APIService, MutatingWebhookConfiguration, ValidatingAdmissionPolicy) and namespaced dependents (Deployment, Service, ConfigMap).
Kubernetes allows a cluster-scoped owner for namespaced dependents — it forbids the opposite direction.

The `pkg/secondarywatch/` package watches those owned resources and enqueues the owning CR when they change.
The enqueuer (`pkg/clusterresourceoverride/enqueuer.go`) resolves the owner by checking the controller `ownerReference` first, then falls back to an owner **annotation** (`OwnerAnnotationKey`).
The annotation fallback exists for objects that cannot carry an ownerRef (notably pod templates inside Deployments).
The watcher also monitors the cluster `APIServer` config and enqueues the primary CR by name when the TLS profile changes.

### Asset Building

The `pkg/asset/` package constructs Kubernetes resource objects (Deployment, Service, ConfigMap, etc.) in Go code rather than using templated YAML.
Configuration values come from the `OperandContext` (namespace, resource name, operand image, version).

### Code Generation

This repo uses `k8s.io/code-generator` (not controller-gen) for generating typed clients, informers, listers, and deepcopy methods.
The script is `hack/update-codegen.sh`, invoked via `make codegen`.
CRD YAML in `manifests/stable/` is maintained by hand, even though some API types carry kubebuilder markers.

## Common Pitfalls

1. **Do not hand-edit generated files.**
   `pkg/generated/**`, `pkg/apis/*/v1/zz_generated.deepcopy.go`, and `bundle/**` are generated.
   Run `make codegen` after API type changes and `make bundle` after manifest changes.

2. **The ClusterResourceOverride CR is a singleton named `cluster`.**
   The reconciler skips CRs with any other name.
   Tests and examples must use this exact name.

3. **Ownership uses standard `ownerReferences`, not annotations.**
   `pkg/runtime/ownership.go` sets controller ownerRefs via `SetOwnerReferences`.
   The owner annotation is only a secondary-watch fallback for objects like pod templates.
   Do not replace `SetController` / `ownerReferences` with annotation-only ownership.

4. **The handler chain order matters.**
   Handlers run sequentially and each depends on the state established by previous handlers.
   Reordering or removing handlers can break reconciliation.

5. **CRD YAML lives in `manifests/stable/`, not a `config/crd/` directory.**
   The CRD files (`clusterresourceoverride.crd.yaml`, `resourceoverride.crd.yaml`) are in `manifests/stable/`.
   These are maintained manually — not generated by controller-gen.

6. **Two separate API groups.**
   `ClusterResourceOverride` uses `operator.autoscaling.openshift.io/v1`.
   `ResourceOverride` uses `autoscaling.openshift.io/v1`.
   Changes to one API do not affect the other.

7. **RBAC is defined in manifests, not via kubebuilder markers.**
   RBAC rules are in `manifests/stable/resourceoverride-rbac.yaml` and `artifacts/deploy/200_rbac.yaml`, not generated from code annotations.

8. **E2E tests require a running OpenShift cluster.**
   They deploy the operator and operand, create CRs, and verify admission behavior.
   They cannot be run with `envtest` or a mock API server.

9. **OLM templates in `artifacts/olm/` contain placeholders.**
   Do not `kubectl apply` them directly.
   Use `make deploy-olm-local` (or the `operator-registry-*` / `olm-*` Makefile targets), which generate manifests under `_output/`.

## Human-in-the-Loop Triggers

Stop and consult a human before:

- **Modifying CRD API types** (`pkg/apis/operator/v1/` or `pkg/apis/autoscaling/v1/`).
  API changes have backward compatibility implications and require regeneration.
- **Changing RBAC permissions** (`artifacts/deploy/200_rbac.yaml`, `manifests/stable/resourceoverride-rbac.yaml`).
  Privilege changes require security review.
- **Modifying webhook configuration logic** (`pkg/asset/webhookconfiguration.go`, handlers in `pkg/clusterresourceoverride/internal/handlers/webhook.go`).
  Webhook changes can break admission for all pods cluster-wide.
- **Changing the handler chain** (`pkg/clusterresourceoverride/internal/reconciler/reconciler.go`).
  Handler ordering and composition affect the entire reconciliation flow.
- **Changes that affect the operand interface**.
  The operator deploys the CRO admission webhook from `openshift/cluster-resource-override-admission`.
  Changes to the ConfigMap format, environment variables, or container arguments must be coordinated with the operand repo.
- **CRD YAML changes** (`manifests/stable/clusterresourceoverride.crd.yaml`, `manifests/stable/resourceoverride.crd.yaml`).
  These are manually maintained and shipped to clusters.

## Paired Changes

| If you change... | Also update... |
|---|---|
| API types in `pkg/apis/operator/v1/` | Run `make codegen`; update `manifests/stable/clusterresourceoverride.crd.yaml` |
| API types in `pkg/apis/autoscaling/v1/` | Run `make codegen`; update `manifests/stable/resourceoverride.crd.yaml` |
| `go.mod` dependencies | Run `make vendor` and commit vendor changes in the same PR |
| Operand Deployment spec in `pkg/asset/deployment.go` | Verify compatibility with the operand image in `openshift/cluster-resource-override-admission` |
| RBAC in `artifacts/deploy/200_rbac.yaml` | Update `manifests/stable/resourceoverride-rbac.yaml` and CSV if applicable |
| CSV in `manifests/stable/` | Run `make bundle` to regenerate bundle manifests |
